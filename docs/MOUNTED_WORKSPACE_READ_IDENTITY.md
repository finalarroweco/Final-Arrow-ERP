# Mounted bank and inventory read identity

A browser tab can retain one operator's mounted workspace while a different tab changes the session cookie. The bank statement/reconciliation and saved snapshot workspaces, branch transfer workspace, order-linked stock hold history, and physical sales delivery/return workspace now attach the mounted `expectedActorId` to their private refreshes, pickers, exports, document navigation and print rechecks. The server authenticates normally and rejects a supplied malformed, duplicate or mismatched actor guard before the private service read. The optional guard does not authorize impersonation or replace current permission checks; ordinary authenticated API requests without it remain supported.

Successful JSON reads identify the authenticated actor outside domain records. Components verify that receipt before adopting a response, alongside their existing request-generation, mounted-state and scope/document checks. Saved bank snapshot downloads identify the reader in an HTTP response header, not by changing immutable version 1/version 2 snapshot JSON or its digest. Allocation, transfer and physical sales mutation/recovery formats are unchanged.

Fresh server-rendered entry pages and cross-module links (for example journal documents and the parent sales order) authenticate the current session and establish new mounted props; they are not background reads into an older mounted workspace. Bound document-detail navigation is checked before data reads. Transfer options and inventory item/branch options are server-rendered from that fresh actor rather than refreshed through an unbound options endpoint. The bank account picker and physical-delivery hold picker are API reads and therefore carry the actor guard.

Explicit order-hold CSV and print actions reread the selected page/filter with the mounted actor guard and current permissions; failed verification stops the output. Printing waits for the verified rows to render and fences stale responses. This change cannot erase information already viewed, printed or downloaded, and it does not automatically reload every tab when a session changes. It is a UI identity-consistency safeguard, not evidence of a server authorization bypass. A separate bounded follow-up binds new bank statement imports to their intended actor; see `BANK_STATEMENT_IMPORT_RECOVERY.md`. No import request bytes or stored hashes are upgraded silently.

Verification includes authenticated session-switch API regressions, optional/direct-read compatibility, strict malformed/duplicate query checks, wrong-actor component responses and generated URL checks. Existing permission-revocation and immutable snapshot tests remain required. Browser automation is not available in this environment because Chromium's Unix-socket requirement is blocked; simulated component tests are not claimed as actual browser acceptance. Database tests use disposable local PostgreSQL only. Deployment, live-data migration and business acceptance remain separate release gates.

Observed authentication loss from an in-flight mutation or recovery check also invalidates that workspace's read state and queued output. Only current 401/403 responses, verified login redirects, or explicit ACTOR_MISMATCH conflicts trigger this boundary; network failures and ordinary business conflicts do not. Each attempt captures the read epoch as well as its actor/scope identity, so an obsolete failure cannot erase newer reauthenticated results. This does not delete or rewrite pending mutation data or relax exact committed-receipt checks.
