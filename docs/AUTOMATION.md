# Explicit finite automation

`/automation` provides personal, scoped, **disabled-by-default** durable jobs. This release installs no jobs, credentials, scheduler, cron task, provider integration, or external action. A separately authorized deployment operator must configure a runner and an external schedule later. An enabled job alone does not establish a running scheduler. The UI reports only whether the runtime flag and credential are present, never a claim of healthy external scheduling.

## Allowed adapters and opt-in

- **Recurring DRAFT invoices:** choose one configured subscription, review its exact current revision, plan lines/prices/tax treatments, terms, calendar, horizon and VAT profile, and select one to 24 period indices within that revision's effective period and full configured horizon. No plan, price, tax, calendar or terms are inferred. Subscription currency must equal the current company base currency; there is no FX conversion. Only original genuine DRAFT invoices are generated. There is no issuing, posting, payment, refund, stock, service activation, entitlement, renewal, replacement or VOID correction. Existing periods (including VOID invoices) are skipped. Past periods requiring backfill are skipped: this adapter has **no backfill authorization option**. Selecting a past start time for the scheduler does not authorize historical invoices.
- **Private alert evaluation:** choose one of the actor's own explicitly enabled rules and review its existing criteria. The original bounded read-only evaluator runs with current source access and its metadata-only terminal receipt. A maximum of 1000 authorized matches applies; an overflow rolls the evaluation back. No external notifications or source writes occur.

Every job begins PAUSED. Creation and enable are separate exact commands. The operator chooses UTC start/end instants, a fixed interval of 1–168 hours, and a budget of 1–100 runs over at most 366 days. These are elapsed UTC intervals, not local civil-time/DST schedules. One run evaluates at most one selected billing period or one rule. A FUTURE or skipped billing period still consumes a run; FUTURE retains the period cursor. Configure sufficient interval/budget for the intended work. Completing the final selected period or exhausting the run budget completes the job. The end instant is exclusive.

Missed ticks coalesce into one current run and the next future UTC tick. They do not create an unbounded catch-up queue. Manual **Queue due run** requires an enabled, due job and uses precisely the same protected runner, lease, horizon, budget and source gates. It cannot advance the time boundary or run from a page read.

Configuration is immutable. To change resource, schedule, period selection or commercial authorization, cancel the old job and create/review/enable a new job. Any subscription configuration/version, plan head/revision, company base currency or full VAT-profile content change pauses execution for renewed authorization. This includes raw content changes without a version increment. A configured future VAT effective date becoming current is allowed only under the unchanged reviewed profile; the ordinary billing service still calculates and validates the exact current preview. Alert evaluation advances its rule version under the same transaction and updates the retained authorization fingerprint; an outside rule version/configuration change requires renewed authorization.

## Authority and privacy

The new `automation:manage` permission is granted only to existing Owner roles and the Owner role of a newly registered account by default. It is separately delegable. No role name alone grants execution access. Current active membership and actual scoped permissions are rechecked at every claim, preparation and effect. Recurring jobs separately require billing read/generate, invoice read/create, customer read in the customer's scope, and plan read in its scope. Alert jobs require the exact owned rule and current source access. A job cannot grant its creator any additional right.

An enabled unattended job uses its retained finite opt-in plus the actor's current account/membership/source authority, **not a browser session**. Ordinary logout does not revoke that separately granted job authorization. Pause/cancel, membership suspension, permission revocation, source disable/configuration change and the finite limits stop future work. No browser token, session ID, runner credential or external secret is stored in a job. Configuration/manual HTTP commands require a current browser session and recheck it after waiting for locks; retained source-operation authority is never a fabricated session.

Only the creator can list a job or its history, and current source grants filter rows **before pagination or lookahead**. No other owner/admin can infer a private rule's counts or labels from this UI. Run history contains statuses, schedule times and attempt counts only, never saved downstream payloads, invoice values, alert observations or credential material. The append-only `AutomationEvent` table is the private audit/attempt history; it is not copied into the broader tenant activity feed. No exports are provided.

An active same-tenant owner of a job can pause/cancel it after source rights disappear. Exact command resolution can recover the original committed/abandoned metadata or permanently abandon an absent command, without source execution. Browser recovery stores the exact original actor/scope-bound command, uses cross-tab Web Locks, and does not replace an uncertain request with a new UUID. User/session/scope changes clear private display state without silently discarding pending commands.

## Durable execution and recovery

This is **at-least-once delivery with exact source idempotency**, not a claim of exactly-once execution.

1. Bounded per-tenant/actor round-robin candidate ranks (oldest due within each rank) claim at most five jobs per runner call (the internal selector permits at most ten). Short claim transactions acquire tenant authorization then job locks with `SKIP LOCKED`; one pending run per job avoids a busy resource taking the whole batch.
2. Each run receives a permanent downstream request UUID. Actor, tenant/company/branch, full exact payload, source version and billing preview hash are persisted before execution. A retry never recomputes a new preview under that UUID.
3. Claims create a 90-second lease with a fresh token and monotonically increasing fence. Every state change checks both the fence and **wall-clock** expiry. A superseded/expired worker cannot finish, replace a payload or overwrite the new attempt.
4. Actual source work and fenced FINISH share one bounded database transaction using the original source service. Expiry before FINISH rolls back the whole transaction. A crash after source statements but before commit has no committed source effect; a lost response after commit is recovered from the durable completed run and source receipt. Source idempotency additionally prevents duplicate invoices/notices.
5. Retry failures record only sanitized codes. Three attempts maximum, with bounded exponential backoff (60 then 120 seconds). A crashed lease can be reclaimed with its original request. Exhausted/unresolved outcomes become UNKNOWN and pause the job; they cannot be re-enabled silently. Review retained original outcomes, cancel the old job, then explicitly authorize a new job if appropriate. Cancellation never rolls back a source action that already committed.

Pause holds an uncompleted run and prevents any effect/finalization while paused. Re-enabling retains the exact outstanding UUID; it does not fabricate a fresh request or extend the horizon. Cancel is terminal and fences pending/unknown work. Already committed effects remain intact. A transaction already holding the job lock finishes atomically before a competing pause/cancel can commit; otherwise the pause/cancel wins and blocks execution.

## Runner integration for a later authorized setup

`POST /api/automation/runner` is a server-only endpoint. It requires **both** `ERP_AUTOMATION_RUNNER_ENABLED=true` and its own server-only `ERP_AUTOMATION_RUNNER_TOKEN` of at least 32 characters. It accepts the credential only in the Bearer authorization header. It does not accept cookies as authority, URL tokens, browser Origin/fetch requests, GET execution or `CRON_SECRET` fallback. Missing/disabled configuration returns 503, invalid authorization 401. Only aggregate batch results are returned; no secret or source data is returned or logged.

`.env.example` leaves the flag false and token empty. No setting has been provisioned by this code. A later authorized deployment should use a dedicated strong credential, private secret storage and a bounded invocation cadence. Do not activate a provider or scheduler as part of migration. Holding a valid runner credential only permits processing previously enabled, currently authorized finite jobs, not choosing an actor, source, scope or payload.

Database credentials are trusted application-server credentials, not end-user SQL authentication. Projection writes require append-only events and enforce scoped authority, finite configuration, immutable identities, source receipts, fences and state transitions. New tables have RLS without public policies; PUBLIC and provider `anon`/`authenticated` grants on tables and functions are explicitly revoked, including under permissive provider defaults. The migration is atomic and creates no enabled state.
