# Private in-app operational alerts

`/private-alerts` is a deterministic, personal observation center. It is not an AI agent. The optional [durable automation engine](AUTOMATION.md) can evaluate one explicitly selected enabled personal rule under a separate finite opt-in job; its runner remains disabled and unconfigured by default. No rule exists after migration. An operator explicitly chooses a permitted source and scope, creates a **disabled** rule, enables it, then presses **Evaluate now**. Opening the center does not evaluate anything. This module does not modify source records, money, stock, orders, subscriptions, ticket state or deadlines. It never sends messages or contacts an external service.

## Explicit criteria

- **Ticket deadline:** tickets currently OPEN or IN_PROGRESS, with an explicit resolution deadline. The operator selects ALL or one priority and enters lookback days (0–3660) and horizon days (0–366). The interval includes UTC calendar dates from today minus lookback through today plus horizon, implemented as inclusive start midnight and exclusive following midnight. It is not a promise that every ticket in the interval is overdue. The displayed due instant is source truth.
- **Subscription review:** ACTIVE, unarchived manual subscription records with a next-review date in the same inclusive UTC calendar-date bounds. Subscription read and independent **current customer read** rights are both required. No billing or renewal inference is made.
- **Stock reorder:** a concrete branch is mandatory. Existing active reorder policies supply the threshold and unit generation. Available = physical minus reserved, with an absent balance treated as zero without creating it. Only available strictly less than minimum matches. Archived/moved sources and changed unit generations do not match. All quantities are calculated in PostgreSQL exact decimal arithmetic and serialized as strings, never JavaScript floating-point numbers. The center does not choose thresholds or recommend a purchase.

Rules are actor/tenant/company/optional-branch bound and their criteria are immutable. Create a new disabled rule for different criteria; disable the old one. A company-wide rule requires company-wide permission for its source kind rather than silently narrowing its scope. Only its owner can read its rules and notices. Different actors with identical source rights cannot read each other's records.

## Observations, not live facts

A notice preserves its initial full source label/reference and its observed date/stock reason without truncating legacy metadata. Its initial observation never changes. “Last matched” is the last successful evaluation instant, not a guarantee about the present source. “Did not match at last evaluation” means a currently visible source did not meet the predicate during that completed evaluation, not necessarily that work was resolved: the date window may have advanced, for example. Acknowledge only marks that actor's private observation as read. There is no automatic acknowledgement or source mutation.

Continuing conditions retain the same notice and acknowledgement. A newly observed match after a completed, authorized nonmatch gets a new episode. A changed deadline sequence, ticket inactive-to-active reopening generation, subscription version or reorder policy version also creates a new observation. Reopening a ticket between evaluations is detected by a database-maintained generation. Stock recovery and recurrence entirely between evaluations cannot be detected without a stock history evaluator; this module does not claim otherwise. Re-enable does not manufacture a new condition episode.

One coherent SQL statement evaluates at most 1001 matching rows. More than 1000 causes the entire evaluation to fail and leaves the previous rule version, notices and evaluation timestamp unchanged. Narrow branch/date criteria and create a replacement rule. There is no partial scan treated as complete. Absence of a deleted/moved/inaccessible source is **unknown**, never treated as resolution. Its retained observation is hidden from all list pages and read filters until its source is again currently visible in that rule's scope. Current source permission filtering happens before pagination. There is no total or global badge that reveals hidden sources; lists use 50 rows plus one authorized lookahead. No export endpoint is provided.

## Integrity and recovery

Every mutation is an immutable request with its expected actor, scope, UUID, rule ID, action, expected version and complete exact payload. Tenant authorization and per-request/per-rule locks precede fresh permission checks. Rule versions prevent stale cross-tab writes; the active-notice unique index prevents duplicate continuing episodes. Observations and rule projections are request-generated; direct writes, deletion and truncation are rejected. Request history is the private immutable audit trail. It is not copied to the broader tenant activity feed.

The browser persists one exact pending capture per actor/company, uses Web Locks to coordinate tabs, retains uncertain outcomes, and only clears a capture after verifying the exact actor/action/IDs/version **and complete request body** in the returned terminal receipt. Interrupted navigation or a newer storage value cannot clear another capture. A fresh browser without Web Locks or usable storage cannot submit mutations. Authentication loss clears visible private content. Focus/page restoration refreshes permissions, and hidden-page transitions clear the current observations. Ordinary network errors do not imply cancellation.

**Limited recovery authority:** `/api/private-alerts/resolve` may report the original committed-versus-abandoned receipt or permanently fence an uncommitted request under active same-tenant membership and exact actor/request/rule ownership, even after source rights disappear. It never executes the requested action or returns source labels, quantities, notice counts, current source status or new data. The receipt contains only the operator's original captured request and its terminal identity/outcome. Wrong actor, wrong body/scope, foreign request collisions and suspended membership fail closed. Ordinary mutation/replay and all notice reads still require current source rights. A delayed original request cannot execute after its UUID has been abandoned. Retained history is not deleted to resolve uncertainty.

The database functions are not a generic SQL-session authentication boundary: only the trusted application server derives the actor from its authenticated session. RLS is enabled without public policies, and PUBLIC plus provider `anon`/`authenticated` table/function grants are revoked atomically, including with permissive provider default grants. Application database credentials must never be exposed to browser clients.
