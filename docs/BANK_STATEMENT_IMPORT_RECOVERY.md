# Bank statement import identity and recovery

New bank import POST requests require `X-Expected-Actor-Id` identifying the mounted operator. Missing/malformed headers fail with `ACTOR_REQUIRED`; a different authenticated actor fails with `ACTOR_MISMATCH` before private source reads or writes. This intentionally changes compatibility for older direct import clients: they must supply the actor header. The strict request JSON and original normalized payload/hash algorithm are unchanged. Existing saved statements remain replayable by their original creator with that same payload and current company-wide ledger read/post permissions. Another currently authorized operator cannot claim a committed request merely by knowing its ID and body.

The server checks current rights while holding the tenant permission lock, then locks the bank account. Committed receipts identify the immutable statement ID/request ID, tenant, company, account, original creator, current actor, normalized request hash, and replay status. The browser verifies every field and locally recomputes the unchanged digest before accepting success. It stores a version 2 actor/company/tenant envelope containing the exact serialized request body; retries send those original bytes and UUID. Lost responses, arbitrary 2xx, mismatched receipts and generic errors never clear that saved request. Duplicate clicks are single-flight; navigation/unmount and changed storage prevent an old response from clearing a newer request.

Legacy `erp-bank-import:<tenant>:<company>` sessionStorage is actorless. Its presence quarantines import actions without parsing/displaying its CSV, sending it, changing it or deleting it. Corrupt envelopes and unavailable storage also block submission. Recovery requires an administrator/operator to investigate the original account and committed records. This release does not infer an actor for old bytes and has no automatic discard or upgrade.

The explicit “Check saved outcome without sending an import” action POSTs the same body to `/api/bank/statements/requests/check`. Despite POST transport, this is a read-only outcome observation: it authenticates the intended actor, checks current company-wide ledger read rights and uses tenant/account locks to compare the immutable hash and creator. `COMMITTED` with a fully verified receipt may clear the local envelope. `UNKNOWN` means only that no committed result was observed while checking. It never clears pending data, cancels a delayed send, reserves/tombstones a UUID, or establishes safe abandonment. The separate explicit permanent-abandon action adds a durable request fence, described in [Bank statement import abandonment](BANK_STATEMENT_IMPORT_ABANDONMENT.md). The check action itself remains read-only and can also observe an exact `ABANDONED` receipt.

Tests cover real two-session cookie switches, same-scope different creator replay rejection, missing actor headers, current permission revocation, exact receipt identity, repeated retries without duplicate audit/source rows, read-only UNKNOWN, legacy quarantine, storage failures, stale callbacks, and hash parity with the original Prisma algorithm (negative zero, exact decimals, UTF-8 and 500 lines). Database/API execution is disposable local PostgreSQL only. Simulated UI tests are not browser acceptance; Chromium is unavailable under the environment's Unix-socket restriction.
